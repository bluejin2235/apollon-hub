# 검색 결과와 표시 출처의 구분

기존 chat 경로는 답변 인용 필터가 끝난 뒤의 cards/notion/wiki 합계를 searchResultCount로 전달했다. 따라서 검색 결과가 있었어도 최종 카드가 사라지면 zero_search로 기록됐다. 원천 검색 실패와 출처 표시 실패를 같은 원인으로 판단하게 만드는 결함이다.

이제 connector 검색 결과 및 질문 필터 이전의 후보 레코드 수를 보존하고 zero_search 판정에는 그 값을 사용한다. 재검색에서 0건이 돌아와도 이전 단계의 양수 관측을 덮어쓰지 않는다. 집계값이 없는 경우는 0으로 가정하지 않는다. 기존 intent/confidence/not_found/unclassified 판정은 그대로다.

메시지 metadata.search_evidence와 failure source_ref에 다음 값을 구분해 저장한다:

- retrieved_candidate_peak: 검색 단계에서 관측한 후보 레코드 수의 최대값. 동일 자료의 카드/원천 레코드가 겹칠 수 있어 고유 파일 수가 아니다. 전체 검색 결과의 누적 합계도 아니다.
- displayed_source_count: 답변 필터 후 표시 출처 레코드 수. 실제 근거가 내용을 뒷받침하는지에 대한 증거가 아니다.

이는 신규 요청의 진단 기록을 고치는 변경이다. 과거 실패 기록을 자동 재분류하거나 답변 생성 품질을 보장하지 않는다. 검색 결과가 있었지만 질문에 맞지 않는 경우는 기존 not_found 신호로 남을 수 있다. 사용자가 요청한 '고래쇼' 사례의 당시 답변 자체를 재생성하거나 유료 LLM 평가를 실행한 것은 아니다.

## 관리자 대화 통계도 같은 근거 사용

운영 관리자 화면을 직접 점검한 뒤 대화 통계의 별도 계산 경로에서 `cards.length === 0`을 검색 실패로 세는 옛 규칙이 남아 있음을 확인했다. `analyzeAssistantMessage`는 이제 유효한 `search_rounds > 0`과 `search_evidence.retrieved_candidate_peak === 0`이 모두 있을 때만 검색 0건으로 집계한다. 검색하지 않은 되묻기, 검색 후보가 있었으나 카드가 숨겨진 답변, 검색 근거가 미저장된 과거 답변은 이 지표로 실패 판정하지 않는다.

이 함수가 쓰이는 대화 이력·관측 지표에도 같은 정의가 적용된다. 과거 기록의 검색 0건 수가 줄어들어도 성능 개선으로 해석하면 안 된다. 정의가 바로잡힌 것이며 미기록을 성공으로 분류한 것도 아니다. UI에 이 집계 범위를 설명하고, 카드 숨김·과거 기록·미실행·실제 0건을 나누는 회귀 검사를 추가했다.
