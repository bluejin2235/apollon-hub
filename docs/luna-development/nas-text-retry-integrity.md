# 본문 추출 재시도와 실행 결과 — 2026-09-26

## 코드에서 확인한 문제

scripts/index-nas-text.ts의 needsWork는 기존 status 문자열이 있으면 수정 시각이 더 새롭지 않은 파일을 건너뛰었다. failed도 이 조건에 들어가므로 NAS 접근이나 파서를 고쳐도 수정되지 않은 파일은 재처리되지 않을 수 있었다.

파일별 실패를 집계한 뒤에도 finishNasTextRun에 done을 전달했다. 이 경우 실행 로그의 실패 건수와 완료 상태가 서로 맞지 않았고 프로세스도 정상 종료했다.

## 수정

- 기존 status가 failed이면 수정 시각이 같아도 재처리 후보에 포함한다.
- 변경되지 않은 ok/empty/skipped의 기존 resume 동작은 유지한다.
- 파일별 작업을 끝낸 뒤 failed > 0이면 기존 예외 경로로 전달해 실행 기록을 failed로 끝내고 프로세스가 1로 종료되게 한다.
- 성공한 다른 파일의 결과를 되돌리거나 전체를 다시 처리하지 않는다.

## 검증

tests/luna/nas-text-run-integrity.test.cjs는 실제 CLI 파일을 VM에서 실행하고 파일/DB 의존성만 모의 처리한다. 기존 실패 파일 재시도, 완료 상태별 건너뛰기, 변경된 파일 처리, no-resume, 일부 실패, 청크 삽입 실패, 읽기 전용 dry-run, 실행 기록 ID가 없는 실패를 검사한다. 실제 NAS·운영 DB·유료 API는 사용하지 않는다. 원격 CI 결과는 PR에 기록한다.

## 적용 범위

운영 데이터에 재추출을 실행한 것은 아니다. main/스케줄러에는 반영하지 않았다. 선택 제한을 처리 필요 여부 판정 이후에 적용한다. 실패 파일이 실행 한도보다 많거나 앞쪽 영구 실패 파일이 한도를 채우면 한 번에 모두 선택되지는 않는다. 영구 실패 파일의 재시도 간격·횟수 제한, 경로의 드라이브별 식별, 청크 교체의 원자성, 실행 기록 저장 오류의 엄격한 처리 등은 남아 있다. 대량 실행 전 소량 검증이 필요하다.

## 후속 수정: 완료된 앞부분에서 멈추는 문제

기존에는 후보를 limit의 배수로 미리 자른 뒤 완료 파일을 제외했다. 앞부분이 이미 완료되어 있으면 그 뒤의 미처리 파일을 계속 놓칠 수 있었다. 이제 기존 메타데이터를 한 번 읽고, 후보 페이지를 순회하면서 완료 파일을 건너뛴 뒤 실제 처리할 파일에 limit를 적용한다. 새 코드는 완료 파일 1,000개 뒤 실패 파일 발견과 T 드라이브 완료 후 P 드라이브 선택을 실제 CLI 테스트로 검증했다. 전체 후보를 항상 메모리에 모으지 않고 작업 한도가 채워지면 조회를 멈춘다.

수정 시각이 더 새로워지는 경우뿐 아니라, 시각이 과거로 돌아가거나 크기/드라이브가 달라진 경우도 재처리한다. 이전 버전 메타데이터가 없거나 비교 불가하면 완료로 간주하지 않는다. 같은 크기와 시각을 유지한 내용 변경은 이 메타데이터 비교만으로 탐지하지 못한다. 물리 파일의 실시간 해시/버전 확인, 실패 재시도 간격, 드라이브 공정성은 별도 과제다.
