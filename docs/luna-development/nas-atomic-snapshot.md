# NAS 원자적 색인 교체

스캐너의 여러 요청에 걸친 직접 색인 교체를 세 개의 service_role 전용 RPC로 대체한다.

1. 수집 시작 전에 클라이언트 UUID로 `nas_snapshot_begin` 호출. 동일 UUID 재시도는 동일 실행이다.
2. 검증을 통과한 수집 결과를 100행씩 `nas_snapshot_stage_batch`에 업로드. 운영 색인은 아직 그대로다.
3. `nas_snapshot_commit`에서 수집 예상 건수와 임시 행 수, 기존 최소 건수 기준, 최신 실행 여부를 확인한다. 삭제·삽입·완료 영수증을 하나의 트랜잭션으로 실행한다. 어느 단계든 실패하면 기존 색인이 보존된다.

같은 완료 요청의 재시도는 저장된 건수를 반환한다. 늦게 끝난 구형 실행은 새 실행을 덮어쓸 수 없다. 드라이브별 advisory lock과 실행 행 잠금으로 프로토콜 요청을 직렬화한다. 최종 교체 중 nas_directory 쓰기는 테이블 잠금으로 직렬화하되 일반 읽기는 허용한다. 다른 드라이브의 교체도 짧은 최종 트랜잭션 동안 대기할 수 있다.

스캐너 PR: https://github.com/bluejin2235/apollon-nas-scanner/pull/1

## 검증 범위

`npm run test:luna-foundation`에 격리 PostgreSQL 엔진 시험을 추가했다. 임시 업로드 중 운영 행 불변, 중복 요청, 건수 불일치, 드라이브 혼입, 삭제 이후 강제 삽입 실패의 rollback, 완료 응답 재시도, 구형 실행 거부, 역할별 권한, 정상 service_role 호출을 확인한다. 스캐너의 실제 함수 시험은 해당 저장소에서 실행한다.

이 시험은 운영 데이터량의 부하 시험이나 실제 다중 연결 동시성 시험을 대신하지 않는다. 현재 운영에 적용하지 않았다.

## 통합 순서

1. 회사 PC의 실제 실행 파일/SHA, 중복 스케줄러, SCAN_PATHS와 UNC 매핑을 확인한다. 하위 폴더를 전체 드라이브로 덮는 기존 모드는 금지한다. 임의 UNC를 SCAN_PATHS에 넣는 구성도 이 버전에서는 지원하지 않으며 SCAN_UNC_T/P를 사용한다.
2. Hub PR #1 기반 시험 의존성을 확보하고 새 migration을 별도 검증 DB에 적용한다. 실제 데이터량으로 준비 공간·최종 트랜잭션 시간·API 시간 제한·동시 읽기/쓰기를 확인한다.
3. 운영 백업/복구 지점을 확인한다. 기존 스캐너와 색인 직접 쓰기 작업을 중지하고 migration을 적용한다. 새 테이블은 RLS를 활성화하고 공개 역할 접근을 차단한다.
4. 새 스캐너를 적용해 1회 실행하고 드라이브별 행 수·대표 파일·삭제 파일·이미지 요약·중요도 재마킹을 점검한 뒤 스케줄러를 재개한다.
5. 배포 후 문제가 생기면 먼저 스케줄러를 중지한다. 스키마는 추가형이므로 남겨 둘 수 있다. 이전 스캐너로 되돌리면 비원자적 삭제 문제가 다시 생기므로 자동 rollback하지 않는다.

## 남은 한계

- 드라이브 단위 원자성이며 여러 드라이브 전체를 묶은 트랜잭션은 아니다.
- 기존과 같이 행 ID는 재생성되고 중요도는 후속 `nas_apply_importance`가 재적용한다. ID 기반 외부 참조가 없는지 배포 전에 점검한다. 운영 스키마에서는 FK 참조는 발견되지 않았다.
- 수집 도중 원본 NAS가 바뀌는 문제, 서로 다른 PC의 UNC 매핑 일치, 본문/이미지/관계/파생 정보의 삭제 전파는 별도 과제다.
- 7일 이전의 미완료 임시 행은 같은 드라이브의 다음 begin 시 정리한다. 스캔을 영구 중지하면 자동 정리되지 않는다. 완료 임시 행은 즉시 삭제하며 작은 실행 영수증은 재시도·순서 판정을 위해 보존한다.
- 실제 PC 소스에서 확인한 드라이브별 기존 건수의 70% 하한과 초기 100건 기준은 유지한다. 실제로 큰 삭제를 수행한 경우 검수 후 별도 처리해야 한다.
